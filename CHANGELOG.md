# Changelog

What changed in each release, newest first. The app (`desktop-v*` tags) and
the browser extension (`v*` tags) are versioned separately.

## Unreleased

- Security: on macOS, a script on the control port or an AI assistant could set the Scheduler's "Run this program when they are done", which dm then ran when the scheduled hours ended. The Scheduler now keeps the program in force when a script was driving the window a moment ago, and says so, as Options already did.
- macOS: dm's window is drawn with GPUI, natively: its menus in the system's menu bar and in the window's top bar beside the search box, the system's own menus, fonts, sheets and settings layout, a window that comes back where it was left, and a third of the CPU at 10,000 rows. Every row of the behaviour contract holds, checked from the release .dmg. The program inside dm.app is now `dm-gpui`; browsers and the login item are pointed at it on its first start.
- Fixed: in Add URL, with a link on the clipboard, an address typed or pasted the moment the dialog opened went in beside that link, not over it.
- Fixed: "Name sent by the server" (B39) named the address's file as the list shows a script's page, `example.com/dl?id=7`, where it is `dl`, as the contract says; and it asked about a name the server never sent ("the name was example.com/plain?id=7, but the server sent plain"), which dm had taken from the address itself. It now sets the server's name against the address's own file name, and No saves the file under that name.
- Tools: `scripts/ui-bench.py` measures the window through the control port (start to first frame, idle CPU, memory, scrolling, Find, CPU with 20 downloads) at 100, 1,000 and 10,000 rows (GPUI migration step A5).
- Inside, no change to what a person sees: the control port's window methods (`ui.*`, what `human-qa.py` and the MCP tools use) are a contract with fixed answers that any window can implement (GPUI migration step A4).
- Inside, no change to what a person sees: the rules the window still kept (the questions a download raises, renames, once-only schedule dates, saved searches' timing, the weekly update check's stamp, one-time hints, the script guard, adding and Undo's bookkeeping, and more) are the application layer's, each with a test of its own (GPUI migration step A3).
- Inside, no change to what a person sees: what the desktop program does that is not drawing (the system's services, the login item, the control port, MCP, the command line, the words and numbers, and the application's `Platform`) is a crate of its own, `dm-desktop-base`, with no window toolkit, so a second window can use it (GPUI migration step A2); the translations moved with it to `desktop/crates/dm-desktop-base/i18n`.
- Inside, no change to what a person sees: the architecture documents and the code agree again (GPUI migration step A1): the window takes the queue's change flag through `dm_shell::app::changes`, the documents give the tick in the order it runs and say which rules are still the window's, and stale comments are corrected.
- Tests: the test that writes Windows' magnet key and opens a link through it passes on Windows. It named dm's program as Cargo spelled it, with a forward slash where the build folder was given one (`D:/dm-target`), and Windows' shell refuses such a command ("Access is denied"); it now names it as dm names itself when it writes the key.
- Inside the browser extension, no change to what a person sees: its background and popup have no JavaScript of their own (the background's WebAssembly is written into its script and started at once, so the Rust registers its listeners itself, and decides which posted forms are kept and puts the panel's code into a page); the rules the two plain-JavaScript page scripts keep (the panel's words, the file kinds a browser shows in the tab, the address and stream patterns, the size caps) are named once in Rust, and a test fails the build where a script differs from them.
- Faster: a download saved to another drive than dm's home (a hard disk beside the system SSD, say) is staged as reference A stages one, each connection's part in a plain file of its own, appended into the download folder at the end, where it was one file copied across: 512 MiB from a local server in 2.1 to 2.9 s from the first request, where reference A took 3.1 to 4.9 s (dm 5.6 to 6.1 s before, the same day). On one drive nothing changes: one file, renamed into place.
- Faster: a download saved to another drive than dm's home (a hard disk beside the system SSD, say) is Completed as soon as its file is in place, without waiting for it to be written out to the disk, as reference A does: 512 MiB from a local server in 5.4 to 6.4 s, where it took 10 to 12.7 s (reference A 3.5 to 4.4 s). Saved on dm's own drive, a finished file is Completed 0.09 s after its last byte. On Windows the file goes to the disk by Windows' own write-behind: asked to flush it, Windows holds the file against every other program for the length of the flush, seconds for a large file on a hard disk, and the window would have frozen with it. On macOS and Linux it is synced after Completed. A power cut in the seconds after Completed can leave the end of such a file unwritten, as it can reference A's.
- Faster: on a server that keeps dropping connections, a connection that comes back goes on from what it has without fetching its last 64 KiB again: that check is for a resume after dm was ended or the power went, and is still made then. 64 MiB at 8 MiB/s with every connection cut after 0.25 to 3 MiB: 8.5 to 8.6 s, 1.1% fetched twice, where it was 9.4 to 10.4 s and 4.8 to 6.7% (reference A 8.3 s, 1.3 to 1.4%).
- Connections per file is now a ceiling, as in reference A: a download opens at most 8 at once, and past 8 adds more (one, then two, then four) only while the last ones added raised its speed, giving them back when they did not. Allowed 16, a server that holds each connection to 1 MiB/s still gets all 16 (6.6 to 6.9 s for 64 MiB, reference A 6.7); a server that shares one speed among them all and cuts them gets 8, in 8.4 s where opening all 16 took 10.1 to 11.1 s (reference A 8.3 s). At the default of 8 nothing changes.
- QA: `scripts/linux-human-qa.sh` runs the whole of `human-qa.py` on Linux, in a Debian 12 container on an X display with Chromium in Edge's place, against a release's own `.deb` and extension (`DM_RELEASE`, each file checked against its `latest.json`), a `.deb` at hand, or a build of the checkout. `human-qa.py` pictures dialogs on X11 (ImageMagick's `import`) and compares the window with Linux baseline pictures of its own (`docs/behaviour-baseline/linux`, drawn from the 0.9.0 release's `.deb`), so B25 is checked on Linux too.

## App 0.9.0, extension 3.3.0

- Fixed: a YouTube video made in another language and dubbed into English came with the English dub, not its own sound (issue #32). YouTube marks the track to play by the language it is asked in, and dm asks in English, so a Spanish video's English automatic dub was marked and its Spanish set aside as a dub. dm now takes the track YouTube names as the original (its address's `acont=original`, or a track id ending `.4`), and the marked track only where none is named; the voice-boosted copy of a track (`vb=1`) is set aside as the loudness-evened one already was. Checked on live YouTube: Spanish and Portuguese videos with English, French, Hindi and automatic dubs each gave their own language; an English video with twenty dubs gave English; single-language videos are unchanged.
- Windows: dm is listed in Settings › Default apps for magnet links and `.torrent` files (and in Windows' "How do you want to open this?"), so a person can choose it there; listing it makes dm the default of nothing and touches no other program's keys, and Uninstall takes it out.
- Browser extension: the hook on a page's `URL.createObjectURL` and `MediaSource` is gone; what it gathered was used by nothing, so dm now changes less of the pages it watches.
- Download details: each file in a ZIP's Contents list has a Take out button, which saves that one file into the folder the archive is going to before the archive is downloaded, fetching only that file's own bytes from a server that serves ranges; it is unpacked (stored or deflated) and checked against the archive's CRC, and a line under the list says where it went or why it could not be taken out (as reference A takes one file out of an archive).
- Downloads: a connection far behind the others (under 0.15 of their average over five seconds) is dropped and asked again, where only one under a sixty-fourth of the whole download was before: a slow connection beside one or two fast ones is now caught too.
- Fixed: a DASH manifest or a Metalink file whose addresses escape `&` as XML does (`&amp;`, `&#38;`) lost those characters, so a signed address such as `v.mp4?a=1&amp;b=2` was read as `v.mp4?a=1b=2` and the download failed; the escapes are now read as what they stand for.
- Fixed: removing a finished download with "Also delete the file(s)" when its file could not be deleted said nothing; "Could not delete …" is now shown.
- Fixed: dm-shell's own tests wrote the person's real settings file (its download folder and When done command); they now use a folder of their own.
- Tests: about 270 more, across the engine, the shell, the protocol and the window, with local servers and temporary folders only.
- macOS and Linux: YouTube's checks and a proxy configuration script run in the system's own JavaScript engine, as they do in Windows' own on Windows: on macOS JavaScriptCore (part of macOS), on Linux WebKitGTK's JavaScriptCore where it is installed (GNOME and WebKitGTK browsers bring it; the rpm recommends it and the Arch package lists it as optional). A fresh install no longer fetches QuickJS from GitHub before its first YouTube download, so it works where GitHub cannot be reached; a Linux without WebKitGTK uses an installed Deno or the QuickJS dm fetches, as before. The engine runs with its JIT off, in a process of its own, as Chakra does on Windows. Checked on live YouTube on macOS, and on Linux with GitHub unreachable and no other engine installed (an ordinary video, two 4K ones with signature-locked streams and a Short, every chosen stream accepted).
- YouTube's weekly check (`youtube-check.yml`) was run by hand on `main` and passed.
- Tests: the YouTube reading tests no longer fail now and then when run side by side (each test process empties its own stand-in folder, not one they all shared).
- Inside, no change to what a person sees: the window asks no server anything itself any more (the update check, a ZIP's files, a file's name and size, a page's links, a video's qualities, a playlist, a site search are the application layer's, all through the proxy and timeout in force), and the application publishes typed download events (added, state changed, completed, failed, removed, progress) to any number of subscribers, measured at 10,000 rows (`docs/architecture/EVENT_FLOW.md`).
- Inside, no change to what a person sees: dm's application layer (`dm_shell::app`) now holds everything the window decided, so another window toolkit can drive the same app (`docs/architecture/ARCHITECTURE.md`; steps 1 to 16 of `docs/architecture/audit.md`): the queue and settings behind `Backend`, what happened between two reads of the list, the schedules, When done, hand-offs from the browser, the control port's rules, every command (its name, label, keys, when it applies, and what it does where no dialog is needed), names and folders a row will get, imports, extraction and the clipboard watch. A row takes its own secrets out before it is shown or sent (`Entry::redacted`). Each step was held to the whole test suite and the behaviour contract (`human-qa.py`, 64 of 64 rows).
- Fixed: YouTube on macOS and Linux with the QuickJS dm fetches: QuickJS took dm's program as an ES module, where YouTube's player could not find its global object ("Cannot find global object"); it is run as a script. The engine's own error is said now, not the last line of its stack.
- Dependencies: tokio-rustls 0.26.6, tokio-util 0.7.20 and webpki-roots 1.0.11, which had fallen out of the lock file (Dependabot #27, #29, #30; #28, #31 and #36 were already in).
- Fixed: a file dm writes for a program it starts at once (the JavaScript that answers YouTube's checks, a run's private cookies) could still be empty when the program read it: the write finished in the background. It is now flushed first (found by the macOS CI runner, `videopage::write_private`). ## App 0.1.0 and extension 3.0.0 — first public release

### The app
- Downloads over HTTP, HTTPS and FTP with several connections at once,
  resumes after a dropped connection, a crash or a restart, and checks each
  part against the server before trusting it.
- A queue with pause, resume, retry, named queues with their own limits, a
  scheduler and a speed limiter.
- Video and audio: HLS streams (with conversion to MP4 where a converter is
  installed), and video sites through an installed the external video tool.
- BitTorrent (magnet links and `.torrent` files) and Metalink with mirrors.
- Sign-ins (Basic and Digest), a `cookies.txt` file, and proxies (HTTP,
  HTTPS, SOCKS4, SOCKS5, or the computer's own settings).
- Categories that sort downloads into folders, checksum verification, a
  download history, and an update check that never installs anything by
  itself.
- Lives in the tray, can start at login, and runs one copy at a time.
- Windows, macOS and Linux (.deb, .rpm, AppImage, Arch).

### The browser extension
- Chrome, Edge, Brave, Vivaldi, Opera and Firefox.
- Hands the browser's downloads to the app. With no app running, the
  browser keeps its downloads, so nothing is lost.
- "Download with dm" on links, media and selections, and a "Download video"
  panel over video players.
- Optional per-site switches: take every download from a site, or hand over
  a site's sign-in.

### Known limitations
- The builds are not code-signed. Windows SmartScreen and macOS Gatekeeper
  warn on first launch; the README says how to open dm anyway.
- dm has not yet been run on a real Windows computer.
